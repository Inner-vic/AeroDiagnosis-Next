# 交互式根因分析 Agent 下一阶段迭代方案

更新日期：2026-09-12<br>
状态：待进入下一轮实施
适用项目：AeroDiagnosis v3

## 1. 项目定位

下一阶段不把系统宣传为能够覆盖真实航空发动机维修业务的通用诊断产品，而将其定位为：

> 以航空发动机气路故障为复杂验证场景，研究模型驱动、知识约束、人在回路、可恢复且可评测的交互式根因分析 Agent。

航空发动机仍然是知识、案例、界面和实验的主要载体；通用 Agent 核心、模型插件协议、
知识检索、根因分析协议和评测框架应尽量保持领域无关，使其未来可以迁移到其他复杂装备。

## 2. 已确认的核心判断

1. 深度学习模型与训练数据域强绑定，数据集 A 的模型不能默认处理数据集 B。
2. 单一模型通常只能输出部件级或故障类别级初步结果，不能直接等同于根因。
3. 将“风扇故障”等短结果直接交给大模型扩写，不能体现 Agent 的诊断价值。
4. 大模型的主要作用是管理差异诊断、调用工具、选择下一项检查、理解工程师反馈和生成报告。
5. 模型结果、知识检索结果和工程师观察都必须作为带来源的证据，而不是不可质疑的事实。
6. 没有真实维修现场并不阻止研究，可先用可复现的虚拟故障场景评测 Agent 轨迹。
7. 下一阶段的重点不仅是增加功能，还要分别测量知识召回、知识抽取、图谱质量和 Agent 效果。
8. 为体现不同能力的真实协作，采用有边界的多 Agent 编排；每个 Agent 必须有独立职责、
   工具白名单、结构化交接和可观测轨迹，不能只在界面上模拟多个角色。
9. 知识问答、知识图谱、知识管理和案例库是长期保留能力，不能被根因分析工作流替代。
10. 用户入口决定工作流：普通问题进入知识问答，上传诊断数据则强制触发数据驱动的根因分析路径。

## 3. 目标与非目标

### 3.1 目标

- 建立模型、数据集、预处理和标签空间的严格绑定关系；
- 支持可信模型插件的注册、验证、推理、版本化和停用；
- 将模型初步诊断转化为可追溯证据；
- 建立“候选根因—检查动作—工程师观察—状态更新”的多轮诊断闭环；
- 建立入口触发、条件路由、并行工作和循环回查组成的多 Agent 工作流；
- 支持手册、向量、图谱、案例和模型结果的多路召回与融合排序；
- 建立知识抽取、知识图谱、检索和完整 Agent 轨迹的分层评测；
- 生成包含完整证据链、不确定性和未解决问题的诊断报告；
- 为论文提供可复现基线、消融实验、失败案例和量化指标。

### 3.2 非目标

- 不声明覆盖任意航空发动机型号；
- 不将仿真数据结果宣传为真实维修效果；
- 不允许模型或 LLM 自动下达维修、放行或适航决定；
- 不允许普通用户上传并执行任意 Python 代码；
- 不在缺乏标签时把异常检测结果包装成精确根因分类；
- 不以增加 Agent 数量、模型规模或页面数量作为成功标准。

### 3.3 必须保留的现有产品能力

- 知识问答：普通自然语言提问、多轮会话、来源引用和证据查看；
- 知识图谱：图谱浏览、实体检索、关系展开、节点详情和来源定位；
- 知识管理：文档上传、版本维护、启用状态、抽取与索引进度；
- 案例库：案例浏览、搜索、详情、相似案例召回和确认后沉淀；
- 参数诊断：手工录入参数并调用现有 Agent；
- 会话记忆：创建、恢复、回读和删除；
- 多主题界面和本机默认/用户自带 LLM API；
- 系统状态、工具轨迹、证据链和运行快照。

这些能力在新版本中可以重新布局和增强，但对应入口、数据和基本操作不得删除。

## 4. 触发式多 Agent 目标架构

```text
用户入口
   │
   v
触发路由器
   ├── 普通知识问题 ──────> 知识问答 Agent ──> 多路检索 ──> 引用核验 ──> 回答
   ├── 文档上传 ─────────> 知识抽取 Agent ──> 图谱/索引 staging ──> 审核发布
   ├── 案例选择 ─────────> 案例分析 Agent ──> 相似案例/知识关联 ──> 案例解读
   └── 诊断数据上传 ─────> 数据分析 Agent ──> 模型路由/插件推理
                                                   │
                                                   v
                                          初步结构化部件诊断
                                                   │
                                                   v
                              ┌──────── 根因协调 Agent <────────┐
                              │              │                  │
                              │              ├── 知识检索 Agent │
                              │              ├── 假设分析 Agent │
                              │              └── 检查规划 Agent │
                              │                                 │
                              v                                 │
                    向工程师提出下一项检查                       │
                              │                                 │
                              v                                 │
                    工程师反馈/补充数据                           │
                              │                                 │
                              v                                 │
                    状态更新 + Verifier                          │
                              │                                 │
                              ├── 证据不足/仍可区分 ─────────────┘
                              └── 完成/升级人工 ──> 报告 Agent ──> 报告/案例
```

### 4.1 触发规则

触发优先采用确定性规则，只有意图模糊时才调用 LLM 分类：

- 请求包含诊断数据文件并点击“开始诊断”：进入数据驱动根因分析；
- 只有问题文本：进入原有知识问答；
- 从案例详情发起分析：进入案例解释或案例辅助根因分析；
- 从图谱节点发起提问：携带当前实体上下文进入知识问答；
- 上传手册或知识文件：进入知识摄取、抽取和审核，不自动进入故障诊断；
- 手工参数录入：保留当前参数诊断路径，也可选择升级为交互式根因分析。

### 4.2 Agent 角色与边界

| Agent | 主要职责 | 允许工具 | 结构化输出 |
|---|---|---|---|
| 触发路由 Agent | 判断入口和任务类型 | 会话/意图工具 | `WorkflowRoute` |
| 数据分析 Agent | 数据画像、质量检查、参数/时序摘要 | 数据解析、统计、绘图 | `DataAnalysis` |
| 模型诊断 Agent | 选择已注册插件并执行推理 | 模型注册表、推理任务 | `ModelInferenceResult` |
| 知识检索 Agent | 并行召回手册、图谱、案例 | 只读检索工具 | `EvidenceBundle` |
| 假设分析 Agent | 展开和比较有限候选根因 | 图谱、证据状态 | `HypothesisRevision` |
| 检查规划 Agent | 选择下一项审核过的检查 | 检查动作库 | `InspectionProposal` |
| Verifier Agent | 审核引用、状态变化和停止条件 | 只读轨迹/证据 | `VerificationDecision` |
| 报告 Agent | 根据冻结轨迹生成报告 | 只读报告数据 | `DiagnosticReportDraft` |

多 Agent 共享的是版本化诊断状态，不直接共享未经裁剪的完整上下文。Agent 间只通过上述 schema
交接。模型推理、候选分数更新、权限、预算和停止条件仍由确定性代码控制。

### 4.3 Loop 的可见化

前端要实时展示当前循环，而不只显示最终聊天内容：

```text
数据分析 ✓ → 模型诊断 ✓ → 知识召回 ✓ → 根因假设 ✓
                                           ↓
报告完成 ← Verifier ← 状态更新 ← 工程师反馈 ← 检查规划
                         └──────── 继续下一轮 ────────┘
```

每个节点显示输入摘要、输出摘要、耗时、工具、证据数量和当前状态；允许查看历史轮次，但不展示
密钥、完整系统 Prompt 或不必要的私有数据。

## 5. 模型插件与数据绑定

### 5.1 插件包

每个模型插件应包含：

```text
model-package/
  manifest.json
  model.onnx | model.pt
  preprocessing.json
  sensor_schema.json
  label_mapping.json
  calibration.json
  model_card.md
```

`manifest.json` 至少记录：

- `model_id`、版本、文件哈希和运行时；
- `dataset_id`、数据集版本与训练集哈希；
- 任务类型：分类、异常检测、健康指数或 RUL；
- 必需/可选传感器、字段顺序、单位、采样率和窗口长度；
- 归一化、缺失值处理和特征工程版本；
- 标签空间与部件映射；
- 适用工况、已知限制和 OOD 阈值；
- 验证集、划分方式、指标与置信度校准方法。

### 5.2 路由与安全

- 上传数据先生成 `DatasetProfile`，再与插件清单匹配；
- 只有字段、单位、采样和任务兼容时才允许自动推理；
- 映射不完全时要求显式字段映射并记录映射版本；
- 无匹配模型时只进行数据质量和通用参数分析；
- 第一阶段优先支持 ONNX 或受控 TorchScript；
- 可信 Python 插件只能由管理员离线安装，不允许通过普通上传入口执行；
- 长时间推理通过后台任务运行，HTTP 请求只负责创建、查询和取消任务。

### 5.3 统一模型结果

模型输出必须是结构化对象，至少包含：

- 模型、数据集、预处理和输入数据版本；
- 适用范围判定与输入质量；
- Top-K 部件/故障类别及校准置信度；
- 异常参数、关键时间段和特征贡献；
- OOD 分数、缺失传感器和警告；
- 可复现实验所需的运行配置和哈希。

该输出进入统一证据层，`source_kind` 标记为 `diagnostic_model`。

## 6. 交互式根因分析协议

### 6.1 显式状态

每个 `DiagnosticSession` 保存：

- 原始数据与质量报告；
- 初始模型诊断；
- 当前候选根因及其状态；
- 每个候选的支持证据、反对证据和未知项；
- 已执行、待执行和不可执行的检查动作；
- 工程师每轮观察及附件；
- 工具调用、模型调用、预算和错误；
- 当前不确定性、升级原因和停止原因。

### 6.2 候选根因

部件级结果必须通过版本化知识图谱、FMEA、手册或已确认案例扩展为有限候选集合。LLM 不得
在集合之外自由创造故障代码。每个候选状态为 `active`、`weakened`、`excluded`、
`confirmed` 或 `unresolved`。

### 6.3 检查动作

每个 `InspectionAction` 记录：

- 动作 ID、名称、适用部件和前置条件；
- 允许的结构化观察结果；
- 能支持或反驳的候选根因；
- 预计时间、成本、风险和信息价值；
- 来源手册、知识版本和人工确认要求。

下一动作可以按以下思想评分：

```text
action_score = expected_information_gain
             - time_cost
             - execution_cost
             - safety_risk
             - repeated_action_penalty
```

初期使用专家规则或人工权重；具备足够案例后再考虑贝叶斯网络或学习排序。

### 6.4 人机循环

1. 模型输出初始部件级 Top-K；
2. 系统扩展候选根因并检索支持/冲突证据；
3. Agent 从经过审核的动作库中选择下一项检查；
4. 工程师回答 `present/absent/uncertain/not_checked`，可补充数值、文本或附件；
5. LLM 将自然语言解析为结构化观察；
6. 确定性状态引擎验证并更新候选，而不是让 LLM 任意修改概率；
7. Verifier 检查本轮动作和状态变化；
8. 满足停止条件后生成报告，否则继续下一轮。

### 6.5 停止条件

- 某一根因达到规定证据门槛；
- 现有条件无法继续区分候选；
- 缺少必要检查或数据；
- 达到工具、轮次、时间或费用预算；
- 检测到高风险情况并转交人工；
- 工程师主动终止。

## 7. 知识抽取研究

### 7.1 抽取流水线

```text
文档解析
→ 章节与表格定位
→ 实体/属性抽取
→ 关系与检查动作抽取
→ 实体标准化与链接
→ schema 校验
→ 置信度与来源绑定
→ 人工审核
→ 版本化发布
```

抽取目标至少包括：部件、故障模式、现象、参数、工况、原因、影响、检查动作、维修参考和
它们之间的关系。所有节点和边必须保留文档 ID、版本、页码/段落或表格坐标。

### 7.2 评测集与指标

建立人工标注的“小而精”抽取金标准，不追求一开始覆盖大量文档。指标包括：

- 实体 Precision、Recall、F1；
- 关系 Precision、Recall、F1；
- 实体链接准确率；
- 属性完整率；
- 来源定位准确率；
- schema 违规率；
- 重复实体率；
- 高风险错误率。

除严格匹配外，另记录别名、边界和层级上的部分匹配；错误按漏抽、错抽、错链、错关系、
错来源和跨版本污染分类。

## 8. 知识图谱稳健性

图谱不只需要“能展示”，还需要经受版本变化、冲突知识和噪声抽取。

### 8.1 稳健机制

- schema 约束节点类型、关系类型、方向和必填属性；
- 不可变知识版本与 active-only 发布；
- 每条事实绑定来源和抽取器版本；
- 同义实体归一化，但保留原始名称；
- 冲突事实并存，不静默覆盖；
- 通过置信度、来源等级和人工状态区分可信程度；
- 支持图谱 diff、审核、回滚和失效标记；
- 查询默认限定活动版本、适用对象和时间范围；
- 未通过审核的自动抽取内容不得作为高风险结论的唯一证据。

### 8.2 稳健性测试

- 随机删除或增加一定比例的边，观察召回和最终诊断下降；
- 注入重复实体、同义词和冲突关系；
- 测试旧版本知识是否错误进入当前检索；
- 测试孤立节点、断链、错误方向和循环关系；
- 比较自动抽取图、人工校正图和去图谱基线。

指标包括图谱一致性、连通性、事实准确率、冲突率、查询稳定性，以及图谱噪声对最终 Agent
成功率的影响。

## 9. 多路知识召回与 Top-K

### 9.1 召回通道

- 关键词/BM25：处理故障代码、参数名和专业术语；
- 向量检索：处理语义相似表达；
- 图谱检索：处理部件、现象、原因和检查动作之间的结构关系；
- 案例检索：处理相似症状、工况和诊断过程；
- 参数/时序分析：提供当前数据中的确定性观察；
- 模型诊断：提供初始部件或类别候选。

### 9.2 推荐融合流程

```text
查询与诊断状态
→ 意图/实体解析
→ 并行多路召回
→ 各路分数归一化
→ 去重与版本过滤
→ RRF 或加权融合
→ 交叉编码器/LLM 重排
→ MMR 多样性控制
→ 证据门槛与动态 Top-K
→ Verifier
```

第一阶段优先实现可解释、可复现的 Reciprocal Rank Fusion（RRF）基线，再与固定权重、学习
排序和 LLM 重排对比。不得仅凭某一路的原始分数直接混排，因为各检索器分数量纲不同。

### 9.3 动态 Top-K

Top-K 不应始终固定。可以由以下因素共同决定：

- 查询复杂度和实体数量；
- 当前候选根因数量；
- 各路分数间隔；
- 证据覆盖度与来源多样性；
- 上下文 Token 预算；
- 是否存在相互冲突的证据；
- Verifier 是否认为证据充分。

先设每路独立候选池，再融合成最终证据集。例如每路召回 10–30 条，融合后重排为 5–12 条，
而不是让某一路提前垄断最终 Top-K。

### 9.4 检索评测

建立“问题—相关证据—必要来源—可接受替代证据”标注集，至少记录：

- Recall@K、Precision@K；
- MRR、nDCG@K；
- 多来源覆盖率；
- 必要证据召回率；
- 重复证据比例；
- 过期版本泄漏率；
- 引用正确率和 claim-evidence faithfulness；
- 延迟、Token 和重排成本。

评测必须分别报告各单路结果、多路融合结果和最终 Agent 结果，避免只看最终回答而无法定位
问题来自抽取、索引、召回、重排还是生成。

## 10. Agent 工程优化

### 10.1 工作循环

使用显式、可恢复的 `plan → act → observe → update → verify → stop/continue` 状态机。每一步
只能产生规定 schema，失败、超时、重试和预算耗尽均进入轨迹。

### 10.2 记忆分层

- 工作记忆：当前诊断状态和近期交互；
- 情景记忆：经过确认的历史诊断案例；
- 语义记忆：文档和知识图谱；
- 程序记忆：检查动作、工具说明和报告规则。

未经确认的聊天结论不能自动进入长期案例库。上下文压缩必须保留否定观察、证据 ID、未解决
问题和动作执行状态。

### 10.3 工具与安全边界

- 工具输入输出均使用严格 schema；
- 读工具与写工具分级，写操作要求明确授权；
- 工具描述包含适用条件、失败语义和例子；
- 检查动作必须来自已审核动作库；
- 报告把维修内容标记为参考，不自动形成维修指令；
- 模型、知识和用户输入均视为不可信数据，防止提示注入；
- 所有结论必须能追踪到模型、观察或知识证据。

### 10.4 可观测性

每个运行记录：Prompt/策略版本、模型身份、工具选择、输入输出摘要、证据变化、候选变化、
重试、延迟、Token、费用、用户反馈和最终状态。敏感凭据和完整私有文档不进入轨迹。

## 11. 虚拟故障环境与评测

### 11.1 场景结构

每个场景包含初始模型输出、隐藏根因、候选根因、允许检查、每项检查的确定性结果、成本、
风险和终止条件。场景必须标记为真实、仿真、文献改编或教学合成。

### 11.2 分层评测

1. 组件测试：schema、工具、状态迁移和停止条件；
2. 知识测试：抽取、图谱、单路召回、融合与重排；
3. 轨迹测试：选问、重复动作、矛盾恢复和记忆一致性；
4. 端到端测试：从模型结果到最终报告；
5. 人工评测：工程师/学生对可理解性、负担和可信度评分。

### 11.3 Agent 指标

- 最终根因准确率和 Top-K 召回；
- 平均诊断轮次、动作成本和信息增益；
- 重复动作率、无效工具率和过早停止率；
- 无依据结论率和错误引用率；
- 矛盾恢复率和记忆一致性；
- 报告忠实度、完整度和人工接受率；
- 延迟、Token 与 API 成本。

### 11.4 对比与消融

- 仅深度学习模型；
- 一次性 LLM 问答；
- 模型 + 一次性 LLM 报告；
- 普通 ReAct Agent；
- 显式根因状态 Agent；
- 去掉图谱、案例、Verifier、记忆或重排器；
- 固定 Top-K、动态 Top-K、RRF、加权融合和学习排序；
- 单 Agent 与确有需要时的多 Agent 版本。

## 12. 前端能力规划

- 知识问答：保留现有对话入口，增加检索来源、引用定位和召回过程；
- 知识图谱：保留图谱浏览，增加路径分析、版本切换、来源和质量提示；
- 知识管理：保留上传与版本管理，增加抽取进度、审核、发布和回滚；
- 案例库：保留浏览与搜索，增加案例详情、相似案例和诊断会话关联；
- 模型注册中心：模型卡、数据绑定、版本、指标和启停；
- 数据集管理：字段画像、映射、质量报告和训练/测试用途；
- 故障场景工作台：数据回放、参数曲线、模型推理和真值控制；
- 交互式诊断台：候选根因、对话、检查动作和证据时间线；
- Agent 流程图：动态显示路由、各 Agent、工具调用、Loop 和结束原因；
- 知识质量中心：抽取审核、图谱 diff、冲突与版本发布；
- 检索调试台：展示各路候选、分数、融合、重排和最终 Top-K；
- 评测中心：数据集、实验配置、指标、轨迹和失败案例；
- 报告中心：报告预览、证据跳转、人工确认和导出。

根因工作台采用四阶段递进导航：数据与模型、初步定位、交互排查、分析报告。阶段可点击跳转，
历史会话直接进入当前可操作阶段；候选、轨迹和报告按任务进度呈现，避免同时堆叠全部信息。

### 12.1 展示模式

为了论文截图、答辩和功能演示，提供明确标记的 `Demo Workspace`：

- 自带教学合成知识文档、图谱、案例和虚拟故障场景；
- 可一键运行一条完整的多 Agent 根因分析轨迹；
- 可切换深色科技、论文浅色和实验室蓝主题；
- 可一键恢复演示数据，避免多次展示后状态污染；
- 所有合成内容在界面和报告中标记为“演示/教学合成”；
- 演示按钮必须调用真实后端和真实工作流，不制作只有外观的空壳功能。

功能数量可以丰富，但每个展示入口至少要具备可执行路径、可解释结果、真实状态和错误反馈。

## 13. 实施阶段与退出标准

### Phase 0：契约与基准先行

- 定义工作流路由、Agent 角色交接、模型插件、数据画像、模型结果、根因、动作和观察 schema；
- 制作首批虚拟故障场景和检索/抽取小型金标准；
- 固化当前系统基线指标。

退出标准：核心 schema 通过契约测试，评测数据版本和指标计算可复现。

### Phase 1：知识质量闭环

- 实现受约束知识抽取、实体链接、来源绑定和审核；
- 实现图谱版本、diff、冲突、回滚和稳健性测试；
- 建立抽取与图谱质量面板。

退出标准：抽取和图谱指标可独立计算，错误可定位到文档与抽取版本。

### Phase 2：多路召回与 Top-K

- 增加 BM25、图谱、案例与现有向量通道；
- 实现 RRF、去重、版本过滤、重排和动态 Top-K；
- 增加检索调试与消融评测。

退出标准：单路与融合结果可比较，必要证据召回率达到预设门槛且无旧版本泄漏。

### Phase 3：模型注册与推理

- 实现可信插件包校验、数据匹配、后台推理和结构化结果；
- 接入一个真实训练模型及其数据集；
- 增加输入质量和 OOD 拒绝路径。

退出标准：相同模型、数据和配置得到可复现结果，不匹配数据被明确拒绝。

### Phase 4：触发式多 Agent 根因分析

- 实现入口触发路由、角色 Agent 编排和共享状态交接；
- 实现候选根因扩展、动作选择、人机反馈和循环状态更新；
- 增加轮次 Verifier、停止条件和 checkpoint 恢复；
- 完成递进式根因工作台、动态 Agent 流程图和报告。

退出标准：知识问题走问答路径，数据上传走根因分析 Loop；虚拟场景可自动跑完，轨迹可恢复、
回放、评分和审计。

### Phase 5：展示整合、论文实验与优化

- 完成 Demo Workspace，确保问答、图谱、知识管理、案例、模型和根因分析都有可执行演示；
- 运行基线、消融、鲁棒性和成本实验；
- 分析失败案例并迭代 Prompt、工具、检索和策略；
- 比较角色合并、角色拆分、学习排序和不同记忆策略。

退出标准：实验配置、数据哈希、逐样本结果、图表和结论全部可复现。

## 14. 风险与应对

| 风险 | 应对 |
|---|---|
| 数据少且型号不明 | 明确数据域，优先做插件适用范围和虚拟场景 |
| 模型结果只有部件级 | 用图谱展开有限根因集合，通过交互逐步区分 |
| 自动抽取污染图谱 | staging、schema 校验、来源绑定、人工审核后发布 |
| 多路分数不可比较 | 分路候选池、RRF 基线、统一重排和消融评测 |
| LLM 编造检查动作 | 只允许从审核动作库选择，Verifier 再核验 |
| 对话变长导致遗忘 | 结构化状态、分层记忆和保真摘要 |
| 多 Agent 增加调用成本和错误传播 | 角色工具白名单、schema 交接、共享状态和逐角色消融 |
| 展示功能多但只有空壳 | 每个入口要求真实后端路径、状态、错误处理和最小验收场景 |
| 论文结论超过证据 | 区分真实、仿真、教学合成数据并限制外推范围 |

本轮已经完成一条可运行、可回放、使用真实 LLM 的知识增强垂直切片：

- 完成模型插件、数据画像、初步模型结果、根因假设、检查动作、工程师观察、角色轨迹和报告契约；
- 完成 SQLite schema v6 的模型注册与根因会话持久化；
- 完成数据上传触发路由、兼容性校验、OOD 拒绝、教学模型推理、受控知识召回和多轮状态更新；
- 完成 LLM 受约束的候选排序、白名单动作选择和报告生成；
- 完成根因分析、模型中心两项一级前端模块，并保留诊断、知识图谱、案例库和知识管理；
